# ADR 0004 — SGBD por níveis

- **Estado:** aceite
- **Data:** 2026-11-27

## Contexto

Há o requisito de suportar quatro SGBD, à escolha do implementador. Em 2026-11-27, os provedores oficiais de Oracle e MySQL estão no EF Core 10 e o Pomelo no 9.

## Decisão

EF Core 11, code-first, um modelo único. **Nível 1:** PostgreSQL e SQL Server, testados em cada PR. **Nível 2:** MySQL e Oracle, que entram quando os respectivos provedores suportarem EF Core 11. O modelo fica pelo denominador comum: sem funcionalidades específicas de um SGBD.

## Alternativas consideradas

- **Os quatro SGBD desde o início com EF Core 10:** rejeitada; o responsável preferiu EF Core 11 e admite que os provedores em falta chegam em breve.
- **Um só SGBD:** rejeitada; contraria o requisito.

## Regras de portabilidade

- todas as `string` têm `HasMaxLength`, excepto texto livre que não é chave, não entra em índice e não é pesquisado;
- todos os `decimal` têm `HasPrecision`;
- `DateTime` sempre em UTC, com `Kind` UTC;
- identificadores com 30 caracteres ou menos;
- sem tipos de coluna, funções ou SQL específicos de um SGBD;
- controlo de concorrência por coluna de versão gerida pela aplicação, não por `rowversion`;
- não depender da distinção entre string vazia e nulo (o Oracle não a faz).

## Consequências

O Nível 2 entra quando houver provedores para EF Core 11. O estado dos provedores verifica-se em cada actualização do Dependabot.

Em máquinas ARM64 o SQL Server não corre em contentor. Aí, o Nível 1 do SQL Server só se verifica no CI.

## Evidência

Teste exploratório com um modelo mínimo (entidade `Factura`) e um projecto de migrações por provedor, partilhando o mesmo modelo. Máquina Windows 11 em ARM64, Docker `linux/arm64` 29.9.3. Código descartável, não versionado, em pasta fora do repositório.

Versões (todas estáveis, nenhuma em pré-lançamento; projectos em `net11.0`): SDK 11.0.100; `Microsoft.EntityFrameworkCore` 11.0.0; `Npgsql.EntityFrameworkCore.PostgreSQL` 11.0.0; `Microsoft.EntityFrameworkCore.SqlServer` 11.0.0; `Microsoft.EntityFrameworkCore.Design` 11.0.0; `dotnet-ef` 11.0.0. Imagens: `postgres:17`; `mcr.microsoft.com/mssql/server:2022-latest`.

### Tipos de coluna gerados (de `pg.sql` e `ms.sql`)

| Propriedade | PostgreSQL 17 | SQL Server |
|---|---|---|
| `Guid Id` (chave primária) | `uuid NOT NULL` | `uniqueidentifier NOT NULL` |
| `Guid EmpresaId` | `uuid NOT NULL` | `uniqueidentifier NOT NULL` |
| `int Numero` | `integer NOT NULL` | `int NOT NULL` |
| `required string NomeCliente`, `HasMaxLength(200)` | `character varying(200) NOT NULL` | `nvarchar(200) NOT NULL` |
| `string? Observacoes`, sem tamanho | `text` (nulo) | `nvarchar(max) NULL` |
| `decimal Total`, `HasPrecision(18, 2)` | `numeric(18,2) NOT NULL` | `decimal(18,2) NOT NULL` |
| `DateTime EmitidaEm` | `timestamp with time zone NOT NULL` | `datetime2 NOT NULL` |
| `bool Anulada` | `boolean NOT NULL` | `bit NOT NULL` |
| Índice único `(EmpresaId, Numero)` | `CREATE UNIQUE INDEX "IX_Facturas_EmpresaId_Numero" ON "Facturas" ("EmpresaId", "Numero");` | `CREATE UNIQUE INDEX [IX_Facturas_EmpresaId_Numero] ON [Facturas] ([EmpresaId], [Numero]);` |

### Outras observações dos scripts

- Chave primária `PK_Facturas` sobre `Id` em ambos; nomes de tabela, coluna, chave e índice iguais nos dois (diferem só as aspas: `"..."` e `[...]`). Os nomes ficam com maiúsculas e minúsculas preservadas, o que no PostgreSQL obriga a citá-los sempre em SQL escrito à mão (razão a mais para não o escrever).
- Nulabilidade idêntica: `NOT NULL` por omissão, excepto `Observacoes`. Pelo `\d "Facturas"` no PostgreSQL, só `Observacoes` aceita nulo.
- Tabela de histórico `__EFMigrationsHistory` com `MigrationId` (150) e `ProductVersion` (32) em ambos, chave `PK___EFMigrationsHistory`; o `MigrationId` leva o carimbo de tempo do momento da geração, por isso os dois projectos têm identificadores diferentes (`20261128015052_Inicial` e `20261128015054_Inicial`). `ProductVersion` regista `11.0.0`.
- O modelo não precisou de `HasColumnType` nem de código por provedor.
- O PostgreSQL envolve a criação do histórico num bloco `DO $EFHistory$` com tratamento de excepções; o SQL Server usa `IF OBJECT_ID(...) IS NULL` e `GO`. Confirma que os scripts não são intercambiáveis.
- Nenhum aviso do EF Core ao gerar as migrações nem ao aplicar no PostgreSQL (a saída só tem «Build succeeded», o bloqueio exclusivo de migração e «Done»). Não houve aviso para `string` sem tamanho.
- `DateTime`: o Npgsql 11.0.0 mapeia `DateTime` para `timestamp with time zone`, o SQL Server para `datetime2`. A leitura e escrita com `Kind` diferente de UTC não foi testada.

### Aplicação

- PostgreSQL 17: `dotnet ef database update` aplicou `20261128015052_Inicial`. O `\d "Facturas"` e a tabela de histórico confirmam as colunas e o índice acima.
- SQL Server: **a aplicação não foi verificada nesta máquina.** A imagem `mssql/server:2022-latest` só existe para amd64. Com `docker run --platform linux/amd64` o contentor `prova-ms` terminou em segundos com código 139: «qemu: uncaught target signal 11 (Segmentation fault) - core dumped» e «Segmentation fault» em `launch_sqlservr.sh`. O SQL Server não corre por emulação em ARM64. Não se usou outra imagem nem outra instância. Os tipos do SQL Server acima vêm do `ms.sql` (script gerado sem base de dados), não de uma base aplicada. O CI (runners amd64) tem de ser o sítio onde o Nível 1 do SQL Server é de facto testado, e o guia de testes avisa que em máquinas ARM64 só o PostgreSQL corre localmente.

### Regras não verificadas por este teste

Identificadores com 30 caracteres ou menos (Oracle), string vazia contra nulo, concorrência por coluna de versão em vez de `rowversion`, e todo o Nível 2 (MySQL, Oracle). Mantêm-se como regras de partida. Também não se testaram queries, apenas o DDL.

### Conclusão

O mesmo modelo, sem código por provedor, gerou migrações para PostgreSQL e SQL Server em projectos separados, e a migração aplicou-se no PostgreSQL. As diferenças relevantes para o modelo são `DateTime` (com e sem fuso) e `string` sem tamanho (`text` contra `nvarchar(max)`). Daí resultam duas emendas às regras: a excepção do texto livre em `HasMaxLength` (`text` no PostgreSQL, `nvarchar(max)` no SQL Server) e o `Kind` UTC em `DateTime` (o Npgsql usa `timestamp with time zone`, o SQL Server `datetime2`, sem fuso, pelo que o fuso tem de ser garantido pela aplicação).
